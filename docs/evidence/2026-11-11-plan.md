
# Next session: from jetsam to a visible screen

## Where the port stands

The storage and privacy path is done on hardware: UFS, userdata GPT, both signed windows, APFS on
the OS volume, the owner-policy authentication of the root, the SystemOS cryptex, the dyld cache
carrier and union, launchd, and its early service list.  The known-good boot arguments are
~-v serial=3 debug=0x14e -no_slto_panic amfi_get_out_of_my_way=1 native-ufs-root=1
native-ufs-diagnostics=1~ with the Data seed whose volume is ~E553E004-A6C6-4992-B474-25EB0F160524~.

Two facts from the last hour decide the next steps:

1. With ~/private/var/ngpu/daemons/com.apple.watchdogd.plist~ (~Disabled~, root:wheel) in the seed
   and ~sheng-gpu-addon=1~ (the OS series' read-only union over ~/System/Library/LaunchDaemons~),
   the first panic moved from ~watchdogd~ to ~memorystatus jetsam_thread: no victim! available
   pages: 3035~.  The boot therefore got past the service that used to end every attempt.
2. A bigger DarwinBoot window behaves as documented but not as hoped: with
   ~[payload.adt] owned_memory_size = 0x20000000~ the loader screen reports ~window 0x20000000~
   and the handoff happens, yet the kernel then dies before the USB console answers; the 4 GiB
   request the board normally carries is not honoured (the loader falls back to 256 MiB).

## Order of work

1. **Prove the job shadowing instead of inferring it.**  Run the jetsam boot and read the console
   ring, or add a one-shot report that lists the launchd jobs that started.  ~watchdogd~ must be
   absent from that list before the memory wall is worth chasing.
2. **Memory.**  ~uke~ records the answer for this class of board: "the kernel owns the 4.75 GiB
   window and jetsam no longer fires at the old ceiling".  Our loader hands the kernel 256 MiB.  Find
   out why ~darwinboot-memory-size~ is ignored (the loader identifies ~/chosen~ by a ~name~ property
   of exactly 7 bytes at depth 1, and a 4 GiB request cannot find a big enough conventional run), then
   grow the owned window in steps - 320 MiB, 384 MiB, 512 MiB - checking after each whether the kernel
   still reaches the console.  A window that works at the loader but kills the kernel means the kernel
   is not prepared to own that range, not that the request was wrong.
3. **Boot hygiene.**  A rebooted board frequently stops at the loader handoff on the first attempt;
   a full power off followed by one normal Android boot clears it.  Treat that as a precondition of
   every hardware run, and read the console only after the kernel has settled, never while it boots.
### Where the memory wall stands (2026-11-11, midnight)

The bounded-window experiment is finished: 256 MiB (the default) reaches userland, 320 MiB and
512 MiB are both accepted by DarwinBoot (the loader screen prints `window 0x14000000` and
`0x20000000`, and the handoff happens) but the kernel then stops at the last early-boot start-up,
the same place the console ring always ends (`lockdown_mode`).  So this kernel cannot own more than
the 256 MiB window it gets today, and the jetsam panic that follows is simply that much memory
minus a 119 MiB kernel, the dyld cache and the Data volume.

Two ways remain, and they are not equivalent:

1. Make the kernel accept a larger owned window (then userland has room).  That is a kernel-side
   question about what grows wrong between 256 and 320 MiB, and the ring says it dies after the
   start-up phase, before `bsd_autoconf` - the same silent stop the policy builds showed.
2. Keep 256 MiB and reduce what userland must hold at once: a smaller dyld cache carrier (the
   cache is the largest single item), or a Data seed without the parts the bring-up does not need
   yet.  The `jetsam` panic is a measurement of pressure, not a policy failure.
### The silent stop has a name: a spin loop in the bootstrap page tables (2026-11-11, 00:20)

The OS series' `native-4k-bootstrap-capacity` patch ends its bootstrap mapping loop with

	Lbootstrap_tables_exhausted:
		// MMU is still off. Stop with the offending cursor/end preserved for
		// the early debugger rather than corrupting memory or forging a map.
		b	Lbootstrap_tables_exhausted

so a boot that runs out of bootstrap page tables does not panic and does not print: it spins with
the MMU off.  That is the shape of every "stops after `lockdown_mode`" boot today, including the
320 MiB and 512 MiB windows, and it is why the console ring always ends without a message.

The native 4 KiB pool is `ARM_PGBYTES * 16`, described in the patch as "two roots plus up to seven L2
pages per 6 GiB mapping", which should cover a 512 MiB window easily - so either the guard trips on
something other than window size, or the mapping loop covers more than the window.  Turning that
spin into a one-line report (a `kprintf` is not possible with the MMU off, but the loop can write to
a fixed UART/framebuffer register) would make the next attempt observable instead of silent; that is
the cheapest next step before any further window experiment.
### The bootstrap spin is not what stops a large window (2026-11-11, 01:00)

The `Lbootstrap_tables_exhausted` spin was instrumented: a device patch (`zzz-bootstrap-exhausted-mark`)
writes a 1024-pixel magenta block into the loader's framebuffer before spinning, so an exhausted pool
would be a visible square.  Booting that kernel with `owned_memory_size = 0x20000000` (512 MiB,
accepted by the loader: `window 0x20000000`) showed only the handoff screen - no magenta - and the
USB console never enumerated.

So the failure with a window above 256 MiB happens earlier than the bootstrap-table guard, before the
console is initialised, and leaves no framebuffer trace.  The instrumentation stays in the tree as a
cheap counter-check for future early-boot questions, but the next step for a larger window is to
instrument `arm_vm_init` / the `boot_args` handoff (where `MemorySize` is first consumed) the same
way instead of guessing again.
### Measured: the policies are the kernel, and the sidecar is the only real saving (01:10)

Segment sizes of the current kernel (`124,649,472 bytes total):

| segment | bytes | what |
| --- | --- | --- |
| `__DATA_CONST` | 74,219,520 | the owner policy hash tables linked in (OS 47 MB + SystemOS 25 MB) |
| `__PLK_TEXT_EXEC` | 20,447,232 | prelinked kext code |
| `__PRELINK_TEXT` | 6,963,200 | prelinked text |
| `__PLK_DATA_CONST` | 3,555,328 | prelinked data |
| `__TEXT_EXEC` | 8,208,384 | kernel code |

So trimming the prelinked roots can return at most about 30 MiB and realistically 10-15, while moving
the policies out with `kernel.macho.vroot` returns about 71 MiB in one step.  Every piece of that route
exists around the kernel and misses only one link: `VerifiedRoot` exposes
`vr_open(envelope, size, key, generation, crypto, view)`, which takes the bundle from memory by design;
`DarwinBoot` publishes the sidecar's physical range as `/chosen/memory-map/RootPolicies`;
`scripts/unixnu/payload.py` already copies `root_policies` to `kernel.macho.vroot` and asks the ADT
generator for the entry.  What is missing is the kernel-side reader that takes that range and calls
`vr_open` - the piece the sm-t970 record attributes to sheng's source storage runtime
(`SourceRootPolicies.cpp`), which this checkout does not have.

Two ways to close it: obtain that runtime, or implement the reader beside the existing owner code in
the OS series (find the memory-map entry, call `vr_open` with the compiled-in anchor, hand the view to
the existing cache-mount path).
### The sidecar swap point is in ShengUfs, not in the sheng runtime (01:40)

The compiled policies are consumed in one place:

	// ShengUfs/NativeUfs.cpp
	extern const uint8_t verified_root_key[];
	const NativeVerifiedBlockPolicy &policy = verified_root_policies[index];   // the 71 MiB of tables
	memcpy (key, verified_root_key, VR_KEY_BYTES);                            // the 395-byte anchor

So the owner path does not need the sheng source-storage runtime after all: the anchor key stays
compiled in (395 bytes), and only the manifest source has to change.  DarwinBoot writes the sidecar's
physical range into the ADT as `/chosen/memory-map/RootPolicies` (a 16-byte {address, size} pairing,
next to `RAMDisk` and `TrustCache`; `devicetree.py` already reserves the placeholder and
`payload.py` already copies `root_policies` to `kernel.macho.vroot`).  A kernel-side reader therefore
has everything it needs:

1. look the pairing up through the device tree (`DTGetProperty` on `chosen/memory-map/RootPolicies`)
   or through the boot arguments memory map the kernel fills from it;
2. hand that range to `vr_open` - already linked in, with `vr_verify_block` - using
   `verified_root_key` and the crypto adapter the probe archive provides;
3. fall back to the compiled tables when the sidecar is absent, so nothing regresses.

Only then can the tables be dropped from `build-verified-root-probe.py`, which removes about 71 MiB
from the kernel and leaves room for userland in the 256 MiB window.
### Correction: moving the policies out of the kernel saves nothing (01:55)

`NativeUfsBlock::configureVerification` already implements a `headerOnly` policy: the manifest may be
just `VR_HEADER_BYTES + VR_SIGNATURE_BYTES` and the hash table is read from the root image at boot
(`readPolicyTable`).  It looks like the 71 MiB answer, but the table is copied into
`kmem_alloc(kernel_map, ...)` before `vr_open` - the same physical pages inside the same 256 MiB
window.  Both volumes (OS and SystemOS) configure their own policy, so both tables are live at
runtime whichever way they arrive.

So the sidecar and header-only routes do not buy memory; the only real increase is a larger owned
window, and that is blocked in the kernel before the console exists.  The next session's entry point
is therefore the early-boot instrumentation already proven with the magenta mark: place marks at
`_start`, after the `boot_args` copy and along `arm_vm_init`, using the loader's framebuffer physical
base while the MMU is off, and count the blocks a 512 MiB boot draws.
### A 512 MiB window gets past the MMU, and the entry probe says so (02:40)

The port's own entry probe settles the question the magenta mark could not: with
`owned_memory_size = 0x20000000` (512 MiB), `panic_screen` off and `entry_probe_reset_delay = 5`, the
screen shows the loader's green bar, the probe's blue bar (kernel entry, MMU off) and its magenta bar
(just before the MMU is enabled), and the board resets five seconds later - which is the probe's own
PSCI reset, armed once the MMU is on.

So a 512 MiB window is not rejected at entry: the kernel reaches the MMU-on point and keeps running.
What it does not do is reach the console, which is why every earlier 512 MiB attempt looked like a
silent hang.  The next refinement is the same probe with `entry_probe_reset_after` pointed at a call
inside `_arm_init` (the call to `arm_vm_init` is at `_arm_init+0x778`); the script reported
"0 call(s)" for that target, so the anchor needs either `--in` tuned to the real function or a
different call site before it can bisect further.
### Bisected: a 512 MiB window only fails inside kernel_bootstrap (04:10)

Seven boots with the port's entry probe (`entry_probe_reset_after`, `--in _arm_init`, three second
PSCI reset) walked the early boot of a 512 MiB window.  Each step reset the board, which proves the
kernel reached that call and returned from it:

| anchor | result |
| --- | --- |
| entry / MMU on | reached (blue and magenta bars) |
| `_arm_vm_init` | reached |
| `_serial_init` | reached |
| `_PE_create_console` | reached |
| `_PE_init_platform` | reached |
| `_ml_map_cpu_pio` | reached |
| `_cpu_timebase_init` | reached |
| `_machine_startup` | **never reached** |

So the whole of `_arm_init` passes at 512 MiB, and the failure is inside `machine_startup`, which only
calls `machine_conf()` and `kernel_bootstrap()`.  `machine_conf` merely stores `mem_size` into
`machine_info.memory_size`, so the stop is in `kernel_bootstrap` before any console output - which is
why the USB console never enumerates at 512 MiB while the same kernel enumerates it at 256 MiB.

The next probe is the same mechanism inside `kernel_bootstrap`: `--in _kernel_bootstrap
--reset-after` its first calls, one at a time, to find where a larger `boot_args->MemorySize` stops it.
