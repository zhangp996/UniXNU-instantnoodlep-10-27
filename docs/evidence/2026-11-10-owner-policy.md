# Owner policy chain on the Linux host

The signed root policy now exists and verifies on the build host; the kernel side still needs the
three symbols listed below.

## Produced

| Input | Value |
| --- | --- |
| owner key | RSA-3072, `build/verified-root-host/keys/owner{,-public}.pem`, openssl |
| host verifier | `build/verified-root-host/verified-root.dylib`, the kit compiled against OpenSSL |
| OS policy | 1,483,785 blocks, sha256 `e5634d04...`, volume `04769D26-2CA0-4825-B443-E2E5F88300F2` |
| SystemOS policy | 806,400 blocks, sha256 `b4908cde...`, volume `8846FE78-2910-4297-AF97-D59BB6F8FC16` |
| probe bundle | `build/verified-root-os-xnu-bundle/libVerifiedRootProbe.a`, both policies, BSD archive |

`scripts/build-owner-policy.py` is the portable form of the macOS-only
`build-owner-os-policy.py`: it reads the raw disk out of the UDIF container with the same reader the
userdata step uses, signs the manifest with the owner key, and re-verifies every block through the
kit's own C before writing `verification.json`.

The SystemOS volume UUID is not in the OS profile; it was read from the APFS volume superblock
(magic `APSB` at offset 32, volume UUID at offset 240 of that block).

## Kernel side still open

With `CONFIG_XNU_VERIFIED_ROOT_PROBE`, `OWNER_ROOT_AUDIT`, `OWNER_ROOT_TRUST`, `OWNER_CACHE_MOUNT`,
`OWNER_CACHE_STARTUP` and the two volume UUIDs set, the link resolves the probe archive but still
needs three symbols the board does not provide yet:

- `boot_progress_poll`, called by the verified UFS read path;
- `native_verified_block_root_authorized(dev_t)` and `native_verified_block_volume_device`, the
  bridge the kernel root decision uses, which the arm64e source-storage package used to provide.

## Linux portability fixes in the probe builder

- `-Wno-unsafe-buffer-usage -Wno-shadow-header -Wno-missing-include-dirs` next to `-Werror`: the kit
  predates the clang that ships with this toolchain;
- the archive is made with `llvm-ar --format=bsd`: `xcrun ar` is GNU ar here, and its long-name
  table makes ld64 ignore the archive ("built for iOS-arm64 ... built for iOS-arm64");
- `mkdir build/xnu/ios-obj/EXPORT_HDRS/libsa`: the record's include path is generated by the kernel
  build, and the probe compile turns the missing directory into an error.
## The verified root reached the device (2026-11-10, evening)

With the owner policy bundle linked and the board bridge in place, the boot no longer needs either
unverified switch: `root-unverified` and `native-ufs-allow-unverified` are gone from the command
line, and the panel shows the launchd error rather than `rootvp not authenticated`. The root volume
therefore authenticated through the signed policy, `/sbin/launchd` was loaded from it, and the boot
stops at the same place as before - the shared cache.

`bootZM` command line: `-v serial=3 debug=0x14e -no_slto_panic amfi_get_out_of_my_way=1
native-ufs-root=1 native-ufs-diagnostics=1 qcom-usb-debug=1 qcom-usb-ctl=1`.

### The bridge

Per the documentation the verified-block bridge belongs to the block driver (`
VirtioMmioBlock` and `RamBlock` carry their own), and the kernel asks it through
`native_verified_block_root_authorized()` and `native_verified_block_volume_device()`. This board
links ShengUfs alone, which exports the authentication hook `native_ufs_block_authenticates()` but
not the bridge, so `package/VerifiedBlockBridge.cpp` supplies the driver-agnostic form -
`verifiedVolumeQuery()` from the VirtIO driver, minus the VirtIO cast - and
`scripts/build-verified-block-bridge.py` adds it to `libShengUfs.a` with the kernel's own C++
flags. It also defines the `boot_progress_poll` hook the verified read path calls.

### Still open

`OWNER_CACHE_MOUNT` and `OWNER_CACHE_STARTUP` are enabled with the SystemOS volume UUID taken from
its APFS volume superblock, yet the dyld cache is still not found, so the SystemOS mount either
fails or never starts. The next step is to observe that path: the SystemOS volume identity is the
first suspect, since it was derived from the APFS superblock rather than taken from a mounted
volume, and the `offline-owner-systemos-mount` patch reports only through kernel state.
## launchd runs: the shared cache is reachable (2026-11-10, evening)

`XNU_OWNER_CACHE_CARRIER` (`offline-owner-cache-carrier`) and `XNU_OWNER_UNION_SYSTEMOS` were the
missing pair. The panel after both were enabled:

```
mount_os exited -- no exit reason available -- (signal 0, exit status 66)
```

The dyld cache message is gone: `launchd` loaded, so `/usr/lib/libSystem.B.dylib` was found through
the carrier the kernel selected, and the boot is now in userland. The first userland failure is
`mount_os` - the helper that mounts the SystemOS cryptex - with status 66 (`EX_NOINPUT`).

The diagnostics used to get here:

- `qcom_owner_report()` (`package/VerifiedBlockBridge.cpp`, called from `kern_exit.c` through
  `patches/xnu/zzz-owner-report.patch`) panics with `native_owner_cache_*` and the `IOMedia` UUIDs
  when `native-owner-report=1`. It showed `stage=6 status=0 mount=0 auth=1 dev=/dev/disk1s1` and
  confirmed both signed volume identities: `disk1s1` is `8846FE78-2910-4297-AF97-D59BB6F8FC16`
  (SystemOS) and `disk3s1` is `04769D26-2CA0-4825-B443-E2E5F88300F2` (OS root) - so the UUID derived
  from the SystemOS APFS volume superblock was right.
- That report must not stay on the command line: it panics before the initproc exit message, which
  hid the very result it was meant to explain.

### Next

`mount_os` exiting with 66 is the first userland question. Its inputs are the cryptex volume, the
boot manifest hash and the data volume, none of which this port supplies yet:
`XNU_OWNER_BOOT_MANIFEST` (`offline-owner-boot-manifest`, "publishes the owner boot manifest hash
from the root and cache devices") is the next documented switch, and `--data-ramdisk` / a Data
volume are the other two inputs the payload step knows about.
### The boot manifest unblocked mount_os

With `XNU_OWNER_BOOT_MANIFEST` (`offline-owner-boot-manifest`) the panel moved on:

```
tzinit_17] exited -- no exit reason available -- (signal 0, exit status 30)
```

`mount_os` no longer fails, so the boot manifest hash it needed is now published from the root and
cache devices. launchd is walking its early service list and the first failure is now `tzinit_17`,
the timezone initialisation helper, with status 30.

That is the Data volume: `tzinit` reads its zone from the data filesystem, and this port's userdata
image carries only the two signed windows (OS and SystemOS), with no Data volume, no
`XNU_OWNER_DATA_MOUNT` and no `--data-ramdisk` seed. The boot has therefore left the storage path
behind and reached the point where the port needs its data filesystem.
### The Data volume needs RamBlock and the newer ShengUfs store API

Following the userdata guide's step 4, a Data volume is a *packed ramdisk seed* handed to the
payload: `--data-ramdisk FILE`, `DBRDISK1` format (`packed_ramdisk.pack`, raw image at most
256 MiB), and `CONFIG_XNU_OWNER_DATA_MOUNT` mounts it at `/private/var`.

The userdata image itself already matches the guide exactly - `SHNGROOT` manifest, OS at
`0x100000`, SystemOS at `0x16a600000`, both 1 MiB aligned, `image_bytes` 9,382,658,048 - so steps
1-3 needed no change.

Step 4 was attempted on the Linux host instead of macOS:

- `mkapfs` (apfsprogs) created a 128 MiB APFS container with volume `Data`,
  UUID `AE5E54BB-7228-466F-8E12-D7B157BFB4DE` (`mkapfs` refuses 32 MiB: "small containers are not
  supported"; 128 MiB works);
- `packed_ramdisk.pack` turned it into a 73,840 byte `.dbr` seed;
- with `XNU_OWNER_DATA_MOUNT` the kernel needs the RAM block driver, so `RamBlock` was added to the
  catalogue selection and `XNU_NATIVE_RAM_BLOCK` enabled. That link then failed on
  `native_ufs_store_write_cached`: the pinned ShengUfs (`1694886` plus this port's commits) exports
  `native_ufs_store_open/read/write/sync` but not the cached write the pinned RamBlock expects.
  Upstream ShengUfs `main` (b11de87) does have it, so the fix is to move the pin and rebase this
  port's driver patches onto that revision - the same commit also dropped the `sheng-` prefix on the
  boot arguments, so the board's `native-ufs-*` names stay valid.

The configuration was reverted to the building set until that pin move is done: the boot still
reaches `tzinit_17` (see above), the Data seed and its tools are ready in
`out/<device>/<os profile>/<config>/data/`.
### The Data volume mounts, and it is empty

The driver pin moved: ShengUfs now builds from upstream `b11de87` (the revision that exports
`native_ufs_store_write_cached`) with this port's three commits rebased on top - the SoC table, the
unverified variant timers and the unverified publication - and the only conflict worth noting was
the media reporting that upstream rewrote (`captureMissingMedia` now takes the window as well).
`RamBlock` is selected again and `XNU_OWNER_DATA_MOUNT` is on with the seed from `mkapfs`.

The panel:

```
tzinit_17] exited -- no exit reason available -- (signal 0, exit status 2)
```

`tzinit_17` moved from status 30 to status 2 (`ENOENT`): the Data volume is up and the helper now
fails because the file it wants is not *in* it. The seed was made from an empty APFS container, so
it carries no `private/var` skeleton - and the guide's step 4 builds that skeleton on macOS, where
`hdiutil` attach gives a writable APFS mount and `make-data-seed.py` copies the OS volume's
`private/var` into it before packing.

Linux has no writable APFS (apfsprogs provides `mkapfs` and `apfsck` only, and `fsapfsmount` is
read-only), so a real Data seed has to come from a macOS host or the repository's macOS workflow.
### The Data seed from the macOS runner carries the boot into userland

The seed that `mkapfs` could not produce came from the repository's own macOS workflow: a
`Data seed` run built `owner-data-32.cdr` with `scripts/prepare-owner-data-fixture.py` (32 MiB APFS,
volume `36C34096-D837-44A1-9A9F-77F1807FA03B`, 39 files of the OS volume's initial `private/var`)
and published it as an artifact. Packed with `packed_ramdisk.pack` (995,408 bytes) and handed to the
payload with `--data-ramdisk`, it moved the boot two steps:

| Boot | Panel |
| --- | --- |
| empty seed | `tzinit_17] exited ... exit status 2` |
| real seed | `watchdogd[114] exited -- exit reason namespace 2 subcode 0x5 description: none` |

`tzinit_17` passes with the real `private/var`, launchd keeps walking its service list, and the
first failing service is now `watchdogd` at PID 114 - the boot is deep in userland. The Data mount
itself reports success: `native_owner_data_prepare()` panics with *offline scratch Data mount
failed* when it fails, and that panic never appeared.

Note for the next step: this kernel panics on the first service that exits, so each boot names one
failing service. `watchdogd` is the current one.
