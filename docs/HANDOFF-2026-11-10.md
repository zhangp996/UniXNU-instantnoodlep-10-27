## Kernel patches this board carries (`patches/xnu/series`)

1. `zzz-defer-framebuffer-mapping` — `initialize_screen()` may not map the panel
   before `pmap_startup()`; it remembers the physical base and maps it from the
   later `initialize_screen(NULL, kPEAcquireScreen)`.
2. `zzz-arm-panic-region-guard` — `check_for_panic_log()` returns while
   `kernel_map == VM_MAP_NULL` (otherwise it maps the `pram` region at VA 0).
3. `zzz-arm-panic-region-late` — `PE_initialize_console()` arms the DT panic
   region once the VM exists.

`scripts/patch-amfi-nopmgr.py` (device repo) must run on every new kernel:
`0x198ad04: 0x940069b8 -> 0x17ffffd2`, otherwise AMFI panics "No PMGR?".

## Traps that cost time (do not re-learn)

- `io_map()` before `STARTUP_SUB_KMEM` uses `virtual_space_start`, which
  `pmap_startup()` has not set yet → returns 0, console stores to address 0.
- The entry probe's assembly dies on its own after the pmap switch: **a probe that
  does not fire is not proof that the kernel died there**.
- Adding the `pram` node makes `check_for_panic_log()` map at VA 0 unless guarded.
- `ml_io_map_unmappable` for the full 10 MiB panel fails in `kmem_alloc`
  (`KERN_NO_SPACE`); the 480-row hand-off (2 MiB) works.
- FD must sit at `0x9E400000` (4 MiB); the shim's `image_size` must stay
  `0x400000`; the DarwinBoot window is 4 GiB at `0xC007C000`, the panel is
  `0x9C000000` (outside it, by design).
- Panic text survives a power cycle in the `pram` region at `0x9F400000`;
  `PanicLogDxe` prints it on the next boot and parks.

## Current task — storage, route: **upstream ShengUfs** (option 1) — the four steps are done

`board.toml` selects `ShengUfs`, `VirtioMmioBlock`, `VerifiedRoot`, and `[kernel] archives` repeats the
complete `profiles/arch/arm64` list before appending the three. The array replaces the inherited one: naming only
the storage components drops corecrypto, the AES original-bindings archive, the mockfs fixture and
libpthread, and the link then fails on `IOAESAccelerator`.

The four steps are in place:

1. `scripts/unixnu/tree.py` links the resolved SoC feed into the tree as `soc/`.
2. `scripts/build-arm-driver.py` adds `-I <tree>/soc/include` for a component whose catalog entry sets
   `soc_headers` (`ShengUfs` now does; the arm64e builder takes the same include).
3. `UniXNU-sm8250-common/include/ufs-soc-table.h` carries the kona entry: host
   `0x1d84000+0x3000`, PHY `0x1d87000+0xe00`, GCC `0x77010 0x77018 0x7701C 0x77020 0x7705C 0x77064 0x7709C 0x770B8 0x770CC`,
   `core_reset` id `0x21` at BCR `0x77000`, no apps-SMMU.
4. `ShengUfs/NativeUfs.cpp` looks the node compatible up in that table, adopts the entry and keeps the
   SM8550 values in `GccUfs.h` as the fallback; the SMMU bypass, display and WiFi stream paths are
   conditional on the entry.

Built and recorded in `docs/evidence/2026-11-10-storage-table-build.md`: `libShengUfs.a` passes `-Werror` and
the arm64-apple-ios17.0 audit, and `kernel/kernel.macho` is byte-identical to the booting image
(`a8c5d42b…`), because `CONFIG_XNU_NATIVE_UFS` is off and the archive is built but not force-loaded.

**The wall is cleared and the image is built.** `CONFIG_XNU_NATIVE_UFS=y`
stopped the XNU link on `__ZTV20IOBlockStorageDevice` and six more base methods, plus the owner-policy
symbols. The storage family now comes from the pinned 21H461 prelink:
`scripts/derive-storage-bindings.py` reads the built object vtable, takes the same slot out of the
original vtable and writes `scripts/data/native-storage-21H461-original-bindings.S` (11 absolute symbols);
`scripts/build-arm-driver.py` archives them with the driver and fails the build if a new storage import
appears. The policy chain is compiled out instead (`XNU_VERIFIED_ROOT_PROBE` off), so the driver
publishes the windows unverified - the signed policies need the userdata image this board has not built.
